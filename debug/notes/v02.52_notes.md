## 1. 依据（log75 定谳）

- pc=lr+fp=0 是 **resume 型 load-jump 摆件**的冻结签名。三个摆件同构：
  `call_on_primordial_stack`、`primordial_to_current_thread` 尾
  （`810c3cbc: push {lr}; … ldr r6,[r1,#0x64]; ldr lr,[r6,#4];
  ldr fp,[r6],#8; mov pc,lr`）、lw_exit 尾。链头一律是
  `[current_thread_desc+0x64]`（ThreadDesc::_stack_pointer）。
- 杀手边不在 pad↔stub 环（log74/75 无 trip 无 magic）。
- **set_current 是所有摆件读 [current+0x64] 之前的唯一提交点**：
  - switch_thread → switch_thread_master_mode/slave_mode → set_current
  - lw_exit 尾 `Thread::set_current(next)`（Thread.cpp:330）
  - 恢复摆件在其后执行。

## 2. 实施

`Thread.cpp` set_current 开头（v231 计数后、commit 前）：

```
候选 value->execution_stack() 非空且 length>0 时：
  lo = field_base(header_size)          // JavaStackDirection==1
  hi = field_base(header_size + length)
  jsp = value->stack_pointer()
  jsp < lo || jsp >= hi  →  重铺：
      gsp = setup_stack_asm(lo)         // 与新生儿路径同基同参
      value->set_stack_pointer(gsp)
      ghost-ring 记录 {id, jsp(旧), lo, pe, caller, act=1}
      _vita_ghost_count++
```

- 防御性：value null / 栈 null / length≤0 → 原路径不动。
- 重铺语义：never-born 幽灵 → 正常进 Java；pe=0 幽灵 → pad→门→
  lw_exit 合法死亡。两条都比吃垃圾恢复 PC 强。
- dump：`vita_thread_dump_ghost`（Thread.cpp 底部）；OS_vita 接
  wd_snapshot（rd1b，qring/dispatch 之后）+ ring_trap（横幅后）。

### 7.3 崩点证据链（thr0 J2ME00001）

```
pc=lr=0x81ee0de4 (堆内 0x81700000+0x7e0de4; log74 基准 +0x7e0dd8, 漂 0xC)
fp=0x00000000    r0=0x81edc2d4 (="Thread-4" UTF 串, 堆+0x7dc2d4,
                   与 log74/75 逐位一致)
r5=0x81401924(gp) r6=0x81edf004   r9=0x81ee0514   r7=0x818b56f4
```

**九槽保存帧逐位闭合**（0x81edefe0..0x81edf000，
`stmdb r6!,{r4,r5,r7,r8,r9,sl,fp,ip,lr}` 所压）：

| 槽 | 值 | 崩点寄存器 | 判定 |
|---|---|---|---|
| r4 | 0 | r4=0 | ✓ |
| r5 | 0x81401924(gp) | r5 同 | ✓ |
| r7 | 0x818b56f4 | r7 同 | ✓ |
| r8 | 0x8119d640 | r8 同 | ✓ |
| r9 | 0x81ee0514 | r9 同 | ✓ |
| sl | 0x818b56cc | r10 同 | ✓ |
| fp | 0x7e120ffc | — | `add fp,fp,r6` 后 0（环回证明：0x7e120ffc+0x81edf004=0 mod 2^32）✓ |
| ip | 0x00000004 | r12=0 | 消费后差异，见下 |
| lr | 0x810a78b8 | — | =`VerifyMethodCodes::new_object+0xb0`，`bl class_format_error`(154) 的返回地址 |

帧内容即 [cur+0x64] 链头：ipe `ldr r0,[cur+0x24]`(pe≠0) →
`sub fp,fp,r6` → `stmdb r6!` 压帧 → `bl shared_entry`（期间 new_object
抛 class_format_error(154) 深埋返回地址）→ 返回侧 `ldm r6!` →
`add fp,fp,r6`（fp 环回 0）→ `mov pc,lr` 吃帧内 lr=堆地址。

等等——lr 槽 0x810a78b8 是 text 合法地址，mov pc,lr 应回 text。
修正：**消费 gadget 是 call_on_primordial_stack 尾**（源码可见）：

```
810c3c88: ldr r1,[r5,#0x40c]      ; _current_thread
810c3c8c: ldr r6,[r1,#0x64]       ; jsp → 指向九槽帧顶
810c3c90: ldr lr,[r6,#4]          ; = 帧槽 ip 之上的 r9? 不——[r6+4]=0x81ee0514??
810c3c94: ldr fp,[r6],#8          ; fp ← [r6]=r9-slot=0x81ee0514??
```

按九槽自上而下顺序（stmdb 压入序 r4…lr，地址降序），帧顶=[r6]=r4
槽？**非也**：stmdb r6!,{r4,r5,r7,r8,r9,sl,fp,ip,lr} 压完后 r6 指向
最低地址=**r4 槽**。对照 dump：0x81edefe0=r4(0)、e4=r5、e8=r7、
ec=r8、f0=r9、f4=sl、f8=fp、fc=ip、0x81edf000=lr。崩点 r6=0x81edf004
= ldm 弹出全部 9 槽后的指针（ldm r6!,{...} 弹 9 槽=36B，
0x81edefe0+36=0x81edf004 ✓）。

**消费序重演**（call_on_primordial_stack 尾 @0x810c3c88）：

```
ldr r6,[r1,#0x64]   ; r6 = 0x81edefe0（帧底=r4 槽）
ldr lr,[r6,#4]      ; lr = [r4槽+4] = r5 槽 = gp！
```

矛盾。最终修正（与寄存器终值全吻合的唯一解）：**消费的是
invoke_pending_entries 返回侧**：`ldm r6!` 弹 9 槽 → r6=0x81edf004，
`add fp,fp,r6` fp=0x7e120ffc+0x81edf004=0，`mov pc,lr` 其中 lr=帧内
lr 槽。但帧内 lr=0x810a78b8 是 text 合法地址——**而崩点 pc=0x81ee0de4
是堆地址**。0x81ee0de4 在全部 fault pages 零存放，它只能来自帧外。

### 7.4 最终机制（唯一自洽解）

帧是"**过去的死亡现场**"——new_object 抛 class_format_error 时
shared_entry 调用链的保存帧，**从未被弹出**（异常展开绕过了 ipe 的
返回侧）。此后 [cur+0x64] 仍指向这具尸体帧。**杀手是 primordial_
to_current_thread 尾**（本代 @0x810c3ef4-0x810c3f00）：

```
ldr r6,[r1,#0x64]   ; r6 ← 尸体帧底 0x81edefe0…（或 +8 处）
ldr lr,[r6,#4]
ldr fp,[r6],#8      ; r6 终值=帧底+8
mov pc,lr
```

若 [cur+0x64] 恰指向 **ip 槽（0x81edeffc）**：lr=[r6,#4]=[0x81edf000]
=帧 lr 槽=…仍 text。若指向 lr 槽（0x81edf000）：lr=[0x81edf004]=
堆外值 0。**都不出 0x81ee0de4。**

→ 0x81ee0de4 的来源只能是**另一次更早的、内容不同的消费**，或
[cur+0x64] 指向的位置不在帧内而在 0x81ee0de0 处（帧外堆区）。
[0x81ee0de0..0x81ee0e04] 全零——pc 指向零页区域执行（0x00000000
指令=andeq）→ 若 pc 从此处取指，第一次取指即 0 字指令，Vita3K
报非法/数据中止——**与"pc=lr"冻结签名一致：取指失败冻结在目标处**。

### 7.5 判决（对照判读表分支③）

1. **ghost-filter 未拦截**：无 reap 记录可看（BSS/TTY 均不可得），
   但崩点签名与 log74/75 逐位同路（r0="Thread-4" 堆+0x7dc2d4、
   pc=lr 堆内、fp=0）——**同一条确定性路径，v02.52 filter 未生效
   于杀手边**。
2. **"set_current 是唯一提交点"前提被证伪**：源码+反汇编证实
   `call_on_primordial_stack` prologue `str jsp,[cur+0x64]`
   （@0x810c3c70）是**第二个 jsp 发布点**，filter 守的是 set_current
   的 value，而杀手读的 [cur+0x64] 可由 call_on_primordial_stack
   在**任意 call_on_primordial_stack 调用**（ipe/shared_entry 内部
   大量使用）直接写入，不经 set_current。
3. **filter 本身逻辑无恙**：反汇编极性/边界/写回与设计一致
   （7.6 节对象级核验通过）。失守在守边位置，不在谓词。
4. **幽灵另有其人**：帧内 lr=class_format_error 返回地址表明
   Thread-4 的出生流程曾在 shared_entry 内抛 class_format_error
   (tag 154)——**验证器拒绝**。Thread-4 的 jsp 从未建立（尸体帧
   顶替），后续 resume 摆件吃尸体。

### 7.6 对象级核验（filter 反汇编逐条对设计）

- `[r3+0x28]`=ExecutionStack 对象非空 → `[r2+4]`=length>0 →

  `cmp ip,r0`/`cmpls r0,r1`/`bcs reap` 极性与 v02.52 设计一致。
- reap 分支：五常量 movw/movt（finish/force_terminated/
  uncaught/lw_exit/landing_pad）内联正确、`str r2,[r3,#0x64]`
  写回、ring 六列+seq/count 更新齐全。
- **set_current 头部 seq 计数器实为 `vita_v231_setcur@0x814b3ba4`**
  （老探针），ghost_seq 在 reap 分支内更新——nm 确认两者并存。
